# MCP-сервер

Подсистема «Сервер MCP» превращает базу 1С в набор инструментов для внешних
ИИ-агентов (Claude Desktop, Cursor, любой клиент [Model Context Protocol](https://modelcontextprotocol.io)).
Агент подключается по HTTP и работает с конфигурацией: читает метаданные,
выполняет read-only запросы, строит диаграммы.


## Две проверки подключения

Пользователь ИБ, под которым веб-сервер открывает сеанс, и логин API ИИконы —
разные настройки. Права сервисного пользователя задаются в базе и публикации;
Basic Auth ИИконы проверяет отдельные реквизиты на форме MCP. Доступ к самой
публикации задаётся средствами 1С и веб-сервера: успешная проверка реквизитов API
не заменяет права пользователя ИБ.

Успех внутренней проверки не подтверждает доступность публикации. Для внешнего клиента
нужен адрес `http(s)://<сервер>/<публикация>/hs/iikona-mcp/rpc` и успешная HTTP-проверка.
401 означает отказ авторизации; 404 требует проверки адреса и публикации HTTP-сервиса.

## Состав

- HTTP-сервис `КИИ_СерверMCPAPI` с тремя точками:
  - `GET /health` — проверка доступности без проверки пароля API;
    вход в саму публикацию по-прежнему определяется её настройками;
  - `POST /rpc` — JSON-RPC 2.0: `initialize`, `ping`, `tools/list`, `tools/call`
    и уведомление о завершении инициализации;
  - `POST /connection` — тот же протокол с входом пользователем целевой информационной базы;
    используется в [подключениях к другим базам](../подключения-баз/README.md).
- Инструменты: `ping`, `get_configuration_info`, `get_metadata_tree`,
  `get_object_structure`, `execute_query` (только чтение), `generate_diagram`.
- Обработка «Сервер MCP: настройки» — пользователь API, пароль, проверка соединения.
- Роль `КИИ_СерверMCPДиагностика` — права сервисного пользователя на необходимые
  данные и использование методов `health.GET` и `rpc.POST`.
- Прокси [iikona-mcp-proxy](https://github.com/andromanpro/1c-ai-connector-mcp-proxy) — мост stdio → HTTP
  для клиентов, которые не умеют HTTP-транспорт напрямую (Claude Desktop).

## Настройка

1. Опубликуйте базу на веб-сервере (стандартная публикация 1С, достаточно
   галки «HTTP-сервисы»).
2. В конфигурации с БСП создайте сервисного пользователя через её штатный
   механизм пользователей и профилей групп доступа. Включите в профиль роль
   `КИИ_СерверMCPДиагностика` и необходимые базовые права принимающей
   конфигурации. БСП может автоматически добавить `КИИ_БазовыеПрава`
   в профиль с базовыми правами БСП. Назначение полного доступа для MCP
   не требуется.
3. «ИИкона» → «Администрирование» → «Сервер MCP: настройки»: задайте отдельные
   логин и пароль API. Они проверяются ИИконой и не являются паролем пользователя ИБ.
   Укажите фактический адрес публикации. Внутренняя проверка подтверждает диспетчер
   в текущей базе; HTTP-проверка обращается к указанной публикации и проверяет весь маршрут.
4. Подключите агента: адрес `http(s)://<сервер>/<база>/hs/iikona-mcp/rpc`,
   Basic Auth с учётными данными из шага 3. Для Claude Desktop используйте
   прокси `iikona-mcp-proxy` (настройка в его README).

## Безопасность

⚠ **Basic Auth передаёт учётные данные в каждом запросе. Наружу сервис
выставляется только через HTTPS** (reverse-proxy с TLS — nginx/Apache/IIS
перед веб-сервером 1С). HTTP допустим только внутри доверенной сети.
Защитный код 1С не проверяет схему публикации — за транспортное шифрование отвечает
инфраструктура публикации.

Что уже делает сама подсистема:

- **Авторизация до диспетчеризации**: неавторизованный запрос не доходит
  до инструментов. Проверка пароля использует безопасное хранилище БСП
  на сервере. Роль MCP не предоставляет прямого чтения пароля или
  защищённой настройки; инструменты продолжают работать с обычными
  правами пользователя ИБ.
- **Ограничение частоты**: 60 вызовов в минуту на вызывающего; при превышении —
  ответ с интервалом повтора.
- **Только чтение**: `execute_query` пропускает исключительно запросы выборки
  (whitelist-валидация текста), число строк результата ограничено.
- **Сокрытие секретов**: значения, похожие на ключи/пароли, в ответах
  маскируются.
- **Аудит**: каждый вызов пишется в журнал регистрации и регистр
  «Сервер MCP — Аудит вызовов» (кто, метод, хеш параметров, результат,
  параметры с замаскированными секретами). Регламентное задание
  «Сервер MCP: очистка устаревших записей аудита» удаляет записи старше
  30 дней — при необходимости другого срока хранения отключите задание
  и чистите регистр своим регламентом.

## Ограничения

- Инструменты работают со своей базой: изменение данных и выполнение
  произвольного кода не предусмотрены.
- Метаданные отдаются по whitelist коллекций (справочники, документы,
  регистры, роли, перечисления, общие модули, обработки, отчёты).


## Проверка подключения и разбор отказов

Проверяйте подключение под сервисным пользователем с его фактическим профилем.
Проверка администратором не подтверждает достаточность прав сервисного профиля.
Установленное расширение должно предоставлять право использования обоих методов
HTTP-сервиса через роль `КИИ_СерверMCPДиагностика`.

Внутренняя проверка на форме и настоящий HTTP-вызов проверяют разные части
подключения. После настройки выполните HTTP-проверку фактического адреса публикации.
Для совместимого клиента MCP проверяются инициализация, получение списка
инструментов и вызов `ping`. Для исправления после аудита подтверждён клиент
MCP SDK 1.29.0 с протоколом `2025-11-25`; поддержку более новых версий протокола
следует проверять отдельно.

- HTTP 401 с обычным ответом веб-сервера требует проверки входа в публикацию 1С.
- JSON-RPC-ответ `Unauthorized` с причиной `credentials_not_configured` означает,
  что обработчик ИИконы не смог получить сохранённые реквизиты API. Проверьте
  их настройку, версию расширения и права сервисного профиля.
- Отсутствие права использования метода проверяется на `health.GET` или
  `rpc.POST`; отдельного права «Использование» у корня HTTP-сервиса нет.
- HTTP 404 требует проверки имени публикации и пути HTTP-сервиса.
- HTTP 405 на отдельный `GET /rpc` допустим: сервис обрабатывает запросы через
  `POST /rpc`. Сам по себе этот ответ не доказывает отказ авторизации.
- Успешное уведомление `notifications/initialized` получает HTTP 202 без тела.
