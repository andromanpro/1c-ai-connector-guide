# ИИкона 1.6.3: повторный замер RAG

11 октября 2026 года. Платформа 1С 8.3.27.1989, БСП 3.1.11, Qdrant 1.18.2 на NAS в локальной сети.

## Что удалось подтвердить

Последние изменения ИИконы ускорили обработку результатов Qdrant примерно в 1,8–1,9 раза.
На 5000 фрагментах медиана полного пути через 1С уменьшилась с 40,4 до 22,4 мс.
Генерация эмбеддингов в этом сравнении не участвовала; её код совпадает с выпуском 1.6.2.

![Результаты сравнения](images/rag-benchmark-2026-10-11.png)

## Условия и границы

Оба способа поиска вызывались из одного внешнего соединения 1С на Windows.
Внутренний поиск включает запрос к файловой базе, чтение и распаковку векторов, точное ранжирование.
Путь Qdrant включает HTTP-транспорт 1С, локальную сеть до NAS, поиск, разбор ответа,
чтение текста найденных фрагментов из 1С и проверку их политики доступа.
Время вызова COM входит с обеих сторон; преобразование готового результата в отчёт не входит.

Подготовлены три независимые базы знаний на 300, 1000 и 5000 фрагментов: всего 6300 точек
одной изолированной коллекции. Размерность — 1536. Векторы псевдослучайные, нормализованы;
исходное зерно Python Random — 20261011. Для каждого размера используются пять запросов,
два прогрева и 20 измерений. Первые десять результатов сравниваются с точным перебором.
Порядок вызовов меняется. p95 рассчитан методом ближайшего ранга по 20 измерениям.

Индекс Qdrant дождался готовности; его фактические параметры и число проиндексированных
векторов сохранены в measurements-2026-10-11.json. При сравнении 1.6.2 и 1.6.3 использованы отдельные
копии 1С с одинаковыми записями и один индекс NAS через изолированный псевдоним.
Ни рабочая база знаний, ни её коллекция не использовались.

Стенд общий рабочий компьютер, а не выделенный сервер. Во время части первых измерений
выполнялась независимая проверка обновления другой копии базы. Абсолютные задержки и p95
следует считать наблюдением этого стенда. Пять запросов с повторами не заменяют большую
выборку запросов или нагрузочную проверку 50–200 пользователей.

## Точность Qdrant на 5000 фрагментах

| Параметры запроса | Медиана / p95, мс | Среднее совпадение | Минимальное совпадение |
|---|---|---|---|
| default | 22.9 / 26.4 | 72% | 60% |
| ef512 | 26.8 / 28.8 | 98% | 90% |
| ef2048 | 28.3 / 29.7 | 100% | 100% |
| exact | 24.6 / 27.0 | 100% | 100% |

Параметры ef512, ef2048 и exact задавались только проверочным сценарием. Интерфейс и
настройки поставляемого продукта не менялись. Точный поиск Qdrant совпал с точным поиском
1С на всех пяти проверенных векторах; медиана около 24,6 мс против 19,4 с — примерно 790 раз.
Это совпадение векторов, а не оценка смыслового качества ответа на реальные вопросы.

Синтетические случайные векторы — трудный случай для приближённого поиска. Полученные
72% по умолчанию нельзя объявлять качеством поиска по реальной документации; точно так же
прежнее «100%» нельзя объявлять универсальной гарантией HNSW.

## Эффект изменений 1.6.3

| Фрагменты | 1.6.2: медиана, мс | 1.6.3: медиана, мс | Отношение |
|---|---|---|---|
| 300 | 37.7 | 19.8 | 1.91 |
| 1000 | 38.7 | 20.8 | 1.86 |
| 5000 | 40.4 | 22.4 | 1.81 |

Результаты двух версий совпали по составу и порядку. Изменён путь восстановления
найденных фрагментов: одна порция чтения, без загрузки и распаковки их векторов.
Получение эмбеддинга, обновление вектора и внутреннее ранжирование совпадают с 1.6.2
по исходному тексту методов. Очередь отправки остаётся поштучной.

## Пакеты и параллельная загрузка: предварительный опыт

Это отдельная проверка транспорта Python REST с wait=true, без обработки очереди 1С.
Повторно отправлялись те же 16 точек размерности 1536: один прогрев, три измерения.
Число точек коллекции осталось прежним. Начальный опыт с 256 точками остановлен после
более трёх минут без готового результата поштучного варианта; в статистику он не включён.
Остановлен только собственный вспомогательный Python-процесс.

| Отправка 16 точек | HTTP-запросов | Медиана, мс |
|---|---|---|
| По одной, последовательно | 16 | 15231.8 |
| По одной, четыре обработчика | 16 | 8145.8 |
| Два пакета по восемь | 2 | 2093.6 |
| Два пакета по восемь, одновременно | 2 | 1450.3 |
| Один пакет из 16 | 1 | 330.2 |

В этом небольшом опыте пакеты дали больший выигрыш, чем только параллельные одиночные
запросы. Три повтора — предварительный результат; выигрыш всей очереди 1С ещё не доказан.
Вариант одного пакета с пулом из четырёх обработчиков фактически выполняет один запрос;
его колебания времени не являются сравнением степени параллелизма.

Для реализации нужны ограниченные порции, проверка актуальной политики, сохранение
новых операций при подтверждении старой версии и последовательность операций одного
фрагмента. В текущей БСП файловая база использует один поток длительной операции;
несколько обработчиков через штатный механизм проверяются в серверной базе.

## Что меняется в статье

Старые 17 секунд и 9 мс относятся к разным границам: ядро 1С без SQL и запрос с localhost
NAS. Их нельзя называть одинаково измеренным пользовательским временем или медианой
повторного сравнения. В актуальный текст подходят новые числа с описанными выше границами
и отдельным указанием точного или приближённого режима. Универсальный порог «до 300
фрагментов быстрее секунды» убран: на этом стенде уже 300 потребовали около 1,15 секунды.

Генерация эмбеддингов внешней моделью и её качество здесь не измерялись. Платных вызовов не было.
Контролируемая первичная заливка по 100 точек использовалась только для подготовки данных;
её время не выдаётся за время индексирования средствами продукта.
