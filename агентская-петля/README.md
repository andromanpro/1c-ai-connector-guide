# Агентская петля

Обычный запрос к модели — один вопрос и один ответ. В агентской петле модель может сначала
попросить данные: дерево метаданных, структуру объекта, результат запроса к базе. ИИкона
выполняет запрошенное, возвращает результат модели, и так по кругу, пока модель не даст
итоговый ответ или не сработает ограничитель.

Так модель ставит диагноз ошибке по настоящей структуре регистра и рисует диаграмму с
настоящими именами реквизитов, а не угадывает их по тексту.

## Где работает

| Где | Что делает модель |
|---|---|
| [Чат с экспертом](../эксперты/README.md#инструменты-в-чате), с включённым флажком «Использовать инструменты» (с 1.7.3) | уточняет метаданные и данные текущей базы перед ответом |
| «Глубокий анализ» ошибки — на дашборде ошибок, в журнале и статистике мониторинга | смотрит структуру объектов из текста ошибки и, если разрешено, данные; пишет диагноз в журнал |
| [Генератор диаграмм](../диаграммы/README.md), режим «по описанию», и программный `СгенерироватьДиаграмму` | запрашивает структуру объектов и строит диаграмму по ней |

Форма генератора идет через петлю с версии 1.6.1; в 1.6.0 и раньше петля работала только
в программном `СгенерироватьДиаграмму`. Если в описании прямо названы объекты
конфигурации (`Справочник.КИИ_МоделиИИ`), генератор еще до петли кладет их состав в промпт,
и модели не нужно тратить на них раунды.

## Что нужно от модели

В карточке модели 1.8.0 на вкладке «Инструменты» должен стоять флажок «Модель поддерживает вызов инструментов»; там же задаётся [выбор разрешённых инструментов модели](../настройка-моделей/README.md#инструменты-модели). В 1.7.4 флажок назывался «Поддерживает инструменты (function-calling)» и находился на вкладке «Генерация». Без флажка:

- инструментальный чат и «Глубокий анализ» отказываются с подсказкой включить флажок или выбрать другую модель;
- генерация диаграммы идет обычным запросом без инструментов.

Флажок ничего не проверяет: он говорит ИИконе, что модель умеет вызывать функции. Если
поставить его модели, которая не умеет, провайдер вернет ошибку на первом же раунде.

Петля работает во всех форматах API: OpenAI, Anthropic, Google, YandexGPT, GigaChat. Для
GigaChat вызовы переводятся в его формат `functions`.

## Инструменты

Модели доступны четыре инструмента [MCP-сервера](../mcp-сервер/README.md):

| Инструмент | Что возвращает |
|---|---|
| `get_metadata_tree` | дерево объектов конфигурации |
| `get_object_structure` | реквизиты, табличные части и типы объекта |
| `get_configuration_info` | имя, версия и поставщик конфигурации, версия платформы, режим совместимости, список расширений |
| `execute_query` | результат запроса на языке 1С, только чтение |

Список закрыт: новые инструменты MCP-сервера в петлю сами не попадают. С версии 1.8.0 модель может использовать только отмеченную для неё часть этого набора. Включённый, но пустой выбор отключает инструменты; ограничения вызывающего кода могут дополнительно сузить выбор.

**Запросы к данным в глубоком анализе выключены по умолчанию.** Модель видит только
метаданные, `execute_query` ей не предлагается. Включает их флажок «Разрешить запросы к
данным в глубоком анализе» в обработке «Настройки мониторинга ошибок» раздела «ИИкона»
(с 1.6.1; раньше — только правкой константы `КИИ_МониторингОшибокНастройки`). В генераторе
диаграмм и при включённых инструментах чата запросы к данным доступны модели.

Запрос выполняется с правами пользователя, который запустил анализ: ограничения доступа к
данным и права конфигурации работают как обычно, привилегированного режима нет. Запрос со
словами `УНИЧТОЖИТЬ`, `УДАЛИТЬ`, `ИЗМЕНИТЬ`, `ВСТАВИТЬ` (и английскими аналогами)
отклоняется, число строк ограничено — не больше 1000.

## Ограничители

Стандартные значения приведены ниже. Начиная с 1.8.1 пределы можно
задать отдельно для каждой модели на вкладке «Инструменты», в группе
«Пределы петли». Ноль сохраняет стандартное значение; отрицательные значения
не записываются. Настройка применяется со следующего запуска петли.

| Ограничение | Значение | Что происходит |
|---|---|---|
| Раундов с инструментами | 5 | цикл переходит к финальному запросу без инструментов |
| Вызовов инструментов за анализ | 10 | лишние вызовы получают ответ «Лимит вызовов инструментов исчерпан» |
| Текст результата одного инструмента | 2000 символов | длинный результат заменяется корректным JSON с признаком усечения и началом текста; обрамление JSON добавляется сверх этого значения |
| Сумма строковых `content` сообщений перед очередным раундом | 24000 символов | при превышении цикл переходит к финальному запросу; это не полный размер сериализованного JSON и не предел токенов |

Когда петля остановилась по ограничителю, ИИкона делает еще один запрос уже без
инструментов: модель должна сделать вывод из того, что успела собрать. Если и он не удался,
ответ — «Анализ прерван по лимиту; вывод не получен.»

До достижения лимита повторный вызов того же инструмента с теми же строковыми
аргументами не выполняется заново и не расходует лимит: модель получает прежний результат.
После достижения лимита оставшиеся вызовы получают сообщение об исчерпании лимита.
Семантически одинаковые JSON-аргументы с разным порядком полей могут считаться разными.

Начиная с 1.8.1 порядок выбора предела такой: стандартное значение,
положительное значение в модели, затем явно переданная опция прикладного вызова.
Прежние публичные вызовы с явными опциями сохраняют приоритет. Настройка модели
используется в чате, генераторе диаграмм и глубоком анализе ошибок.

Увеличение числа раундов или размера результатов может повысить расход токенов
и длительность ответа. Для больших списков метаданных лучше сначала использовать
постраничную выдачу, описанную ниже.

### Большие списки метаданных: 1.8.1

Инструмент `get_metadata_tree` принимает необязательные `offset` и `limit`.
Для первой страницы передайте `offset: 0`, например с `limit: 20`. Размер страницы
должен быть целым от 1 до 200. Если задан только `offset`, размер равен 20;
если только `limit`, смещение равно нулю.

Ответ содержит объекты страницы и поля `total_count`, `returned_count`,
`has_more`, `next_offset`. Пока `has_more` истинно, передавайте `next_offset`
в следующий вызов с тем же фильтром. Не меняйте конфигурацию между страницами:
порядок соответствует её текущим коллекциям. Без обоих параметров сохраняется
прежний формат ответа.

Список уже имеет краткий состав: имя, синоним, тип, каноническая ссылка и
происхождение объекта. Реквизиты и табличные части запрашиваются отдельно
через `get_object_structure`. Для списка справочников используется
`filter: "Catalog.*"`; счётчики категорий позволяют узнать количество без
перебора всех страниц.

В петле `get_metadata_tree` получает страницу размером 20, если модель не
передала `offset` и `limit`. Ограничение текста результата продолжает действовать:
ИИкона уменьшает страницу по целым объектам и исправляет `returned_count`,
`has_more` и `next_offset`. Переходите по полученному курсору; запрошенный
`limit` не гарантирует такое же количество фактически переданных объектов.

Если даже один объект не помещается в предел текста, ответ содержит ошибку,
нулевой `returned_count` и `has_more: true`. Это не конец списка.
Увеличьте предел результата в модели; повторение прежнего курсора с тем же
пределом не даст новых объектов. Фильтрация и права подключённых баз сохраняются.

### Таймаут и длительность всей петли

Таймаут модели относится к отдельному HTTP-обращению к провайдеру. У подключения
к другой базе есть свой таймаут запроса к источнику. Длительность всего ответа
складывается из обращений к модели, инструментов и обработки результатов,
поэтому она может превышать таймаут одного обращения.

Пределы раундов, вызовов и размеров данных ограничивают работу петли, но не
являются общим таймером в секундах. При ошибке выясните по связанным записям
журнала, какой вызов завершился таймаутом. Количество объектов и расчётное
число страниц сами по себе не показывают, сколько страниц модель получила.
Увеличение таймаута без такого разбора может лишь продлить ожидание.

Ошибка инструмента, например неверный запрос, не прерывает петлю: текст ошибки уходит
модели, и та может исправить вызов в следующем раунде.

## Что остается в базе

- **Журнал запросов ИИ** — каждый раунд отдельной записью: токены, время, стоимость. Раунды
  одного анализа связаны полем «Корреляция агента». Ответы петли не берутся из кеша.
- **Журнал регистрации**, событие `КИИ.АгентАнализа.Вызов` — каждый вызов инструмента:
  идентификатор анализа, имя инструмента, успех, пометки «(из кеша петли)» и «отклонен:
  лимит». Ошибки инструментов пишутся предупреждением в `КИИ.АгентАнализа`: по умолчанию
  мониторинг собирает только уровень «Ошибка» и их не видит. Если в настройках мониторинга
  включен сбор предупреждений, эти записи попадут в журнал ошибок наравне с другими.
- **Журнал мониторинга** — результат глубокого анализа: секция «[Глубокий анализ дата]» с
  числом раундов и вызовов в поле «Описание от ИИ». Повторный глубокий анализ заменяет
  прежнюю секцию, результат автоанализа остается ниже.

## Персональные данные

Все раунды одного анализа идут через
[контроль персональных данных](../контроль-персональных-данных/README.md) с общим набором
подстановок: одно и то же ФИО во всех раундах заменено одинаково. Результаты инструментов,
в том числе строки из `execute_query`, тоже уходят модели подстановками.

В чате окончательный текст для человека восстанавливается; машинный ответ и записи
журналов сохраняют подстановки. Токены всех раундов суммируются в ответе чата.

Диагноз в журнале мониторинга остается с подстановками. В коде диаграммы подстановки
возвращаются к исходным значениям: этот код читает и правит человек.
